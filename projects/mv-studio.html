01 — Overview

Begining life as a collection of CLI tools I used during my summer internship on a machine vision project, I decided to create a GUI in my own time to speed up my work. Stakeholders noticed and saw value in developing it further for internal use at the company.

The CLI pipeline's stages were already thin wrappers over importable functions from the core ML library I had been working on, so the backend imports them and gets structured results instead of scraping stdout. That generic ML core was extracted into its own package, and a Flask API, a job runner, a database and a React app sit on top of it.

It's deliberately single-tenant, but each seam (job runner, storage, database) is shaped so that a shared multi-user GPU server is a refactor, not a rewrite.

02 — Under the hood

  • Jobs run outside the request cycle. Each training, evaluation or export job is its own subprocess, so a native crash can't take the API down. Logs stream to the browser over SSE, and you can reattach after a reload.
  • One GPU, one job. Heavy jobs are serialised behind a lock, and a CUDA out-of-memory error becomes an actionable "reduce batch size" message instead of a dead worker.
  • Content-addressed storage. Images and labels are keyed by hash, so the same image ingested twice is stored once. Deletion is a database cascade plus reference-counted cleanup, so orphaned files can't hang about.
  • One detector interface. YOLO, RF-DETR and a dummy model sit on the same protocol, covering both boxes and instance masks. Adding an inference-only model is one adapter file, defining a training regime is a new class with a decorator.
